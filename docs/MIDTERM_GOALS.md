# InodeFence — 11월 2일 중간발표 공동 개발 목표

**기준일:** 2026년 10월 23일  
**중간발표:** 2026년 11월 2일  
**최종 연구 마감:** 2026년 11월 30일

## 1. 중간발표의 최종 목표

11월 2일까지 **InodeFence의 핵심 연구 아이디어가 실제 프로그램으로 연결되어 작동하는 것을 입증한다.**

우리의 연구 가설은 다음과 같다.

> TAR 아카이브 해제 과정에서 발생하는 중간 파일시스템 상태 시퀀스를 피드백으로 활용하면, 동일한 퍼징 예산에서 더 유의미한 후속 입력을 선택할 수 있다.

중간발표에서는 이 가설의 최종적인 성능 우위까지 입증하는 것을 필수 조건으로 삼지 않는다.

대신 실제 node-tar를 대상으로 다음 과정이 연결되어 실행되는 것을 목표로 한다.

1. TAR 입력 생성 및 변형
2. 격리된 환경에서 실제 node-tar 실행
3. 각 entry 처리에 따른 중간 파일시스템 상태 관찰
4. inode identity 및 C0/C1/C2 Oracle 평가
5. 관찰된 상태 시퀀스를 피드백으로 변환
6. 피드백을 이용한 다음 mutation 선택
7. 실행 결과와 피드백 선택 근거를 재현 가능한 형태로 출력

**단순히 Oracle이 동작하는 것을 보여주는 데서 끝나지 않고, 상태 관찰이 다음 입력 선택에 실제 영향을 미치는지 확인하는 것이 핵심이다.**

---

## 2. 필수 구현 범위 (P0)

### P0-1. 실제 node-tar 실행

- 고정된 node-tar 버전을 대상으로 실행한다.
- TAR 입력이 실제 extractor에 전달되어야 한다.
- 격리된 실행 환경을 사용한다.
- 실행 결과와 실패 원인을 수집할 수 있어야 한다.
- 정상 입력에 대한 최소한의 반복 실행이 가능해야 한다.

### P0-2. 중간 파일시스템 상태 관찰

- TAR 전체 해제 전후 비교만으로 끝나서는 안 된다.
- entry 처리 과정에서 발생하는 중간 상태를 관찰해야 한다.
- path, entry type, link 관계, inode identity 등 필요한 특징을 추출한다.
- 실제 관찰한 상태와 추론하거나 재구성한 상태를 명확히 구분한다.

### P0-3. Oracle 검증

- 기존 C0/C1/C2 판정의 의미가 유지되어야 한다.
- 정상 사례와 의도적으로 구성한 검증 fixture로 판정의 정확성을 확인한다.
- Oracle의 탐지 결과와 실제 취약점 재현 성공을 혼동하지 않는다.

### P0-4. Feedback 기반 Mutation

- 중간 상태에서 추출한 특징을 mutation 선택 과정에 연결한다.
- 같은 입력 상태에서 피드백에 따라 어떤 mutation이 선택되었는지 확인할 수 있어야 한다.
- 선택 근거를 로그나 결과 파일로 남긴다.
- 실제 feedback이 적용되지 않았다면 적용된 것으로 발표하지 않는다.

### P0-5. End-to-end 데모

하나의 명령 또는 명확한 실행 절차로 다음 흐름을 재현한다.

`입력 생성 → node-tar 실행 → 중간 상태 관찰 → Oracle 평가 → Feedback 생성 → 다음 Mutation 선택`

발표 전에 동일한 실행 절차가 반복적으로 성공하는 것을 확인한다.

## 3. 추가 목표 (P1)

P0가 완료된 경우 다음을 진행한다.

- A: Random mutation
- B: Structure-aware mutation
- C: Intermediate FS state-aware mutation (InodeFence)

세 전략을 동일한 seed, 실행 예산, Oracle 조건에서 비교하는 소규모 실험을 수행한다.

비교 지표는 중간 상태 다양성, 고유 상태 전이, 유효 입력 비율, 의미 있는 Oracle 이벤트 발견 정도 등을 사전에 정의한다.

**P1은 중간발표의 추가 성과이지 P0 구현을 희생하면서까지 진행할 작업은 아니다.**

N01 historical rediscovery 역시 중간발표의 필수 성공 조건에서 제외하되, 11월 30일 최종 연구 일정에 맞춰 계속 추진한다.

### 주언 — Feedback / Evaluation

- 중간 상태 데이터의 피드백 변환 경로 검증
- Feedback 기반 mutation 선택 기능 연결
- A/B/C 비교 실험의 공통 조건 및 측정 방식 정의

- 실제 node-tar 실행 환경 검증

- 격리 환경과 실행 경로의 연결 확인
- 재현 가능한 실행 명령 및 환경 제공
- 실패 원인과 실행 증거 확보

### 민찬 — Observation / Oracle / Demo

- 중간 entry 상태 관찰 기능 검증
- C0/C1/C2 Oracle의 정상·경계 사례 확인
- 관찰 결과의 시각화 및 데모 구성
- 실제 프로그램 실행 시연과 녹화 준비

담당 영역은 우선 책임자를 뜻하며, 인터페이스 연결과 최종 검증은 서로 협력한다.

## 5. 개발 및 GitHub 운영 원칙

1. 현재 main을 기준으로 전체 구조와 실행 경로를 먼저 파악한다.
2. 진행 중인 PR은 실제 추가되는 기능과 의존관계를 확인한 뒤 통합한다.
3. 중복 PR과 오래된 브랜치는 고유 변경사항 및 복구 가능성을 확인하기 전까지 삭제하지 않는다.
4. 새로운 작업은 목적과 완료 조건이 명확한 브랜치에서 수행한다.
5. main 직접 push는 금지하며, 검증된 PR만 병합한다.
6. 불필요한 감사·계획 문서 생산은 줄이고 실제 코드 및 실행 결과를 우선한다.
7. 기존 기능의 안정성을 해치면서 발표 데모만을 위한 임시 구현을 추가하지 않는다.

모든 개발 PR은 다음 질문에 답해야 한다.

**"이 PR을 병합하면 어떤 기능을 실제로 실행하거나 검증할 수 있게 되는가?"**

## 6. 완료 판정 기준

11월 2일 시연을 완료했다고 판단하려면 다음 사항을 확인한다.

- [ ] 실제 node-tar를 대상으로 한 실행이 성공한다.
- [ ] 중간 파일시스템 상태를 관찰하고 출력한다.
- [ ] Oracle 판정이 검증된 fixture와 일치한다.
- [ ] 관찰된 상태가 mutation 선택 과정에 실제로 전달된다.
- [ ] 피드백에 따른 선택 결과를 확인할 수 있다.
- [ ] 동일 조건으로 데모를 재현할 수 있다.
- [ ] 실행 환경, 고정 버전, 테스트 결과를 기록한다.
- [ ] 발표에서 구현·테스트·실험 검증 수준을 구분한다.

P0 중 일부가 완료되지 않은 경우, 해당 기능을 미완성으로 표시하고 검증된 범위까지만 시연한다.

우리는 단순히 많은 코드를 작성하거나 PR을 병합하기 위해 개발하지 않는다.

11월 2일에는 **InodeFence의 연구 아이디어가 실제로 구현되고 실행된다는 것을 입증**하고, 11월 30일까지 그 효과를 실험적으로 평가할 기반을 완성하는 것이 목표다.

우선순위는 다음과 같다.

**실제 동작 → 재현 가능성 → 기능 정확성 → 실험적 검증 → 문서화**

이 목표를 기준으로 현재 작업의 우선순위와 팀원별 일정을 조정한다.
