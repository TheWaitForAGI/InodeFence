## 3. 사전등록 대비 편차 공개

**편차 1. 시간 값의 시계.** `step_wall_seconds`와 런처 wall은 CLOCK_MONOTONIC이고, 이 호스트에서 실시간보다 빠르게 갔다. 당일 배율은 합산 1.0914, 셀별 1.0855~1.0964다(관찰: 런처 wall ÷ 같은 구간 로그 파일의 생성→마지막 쓰기). 원인은 미확인이고 호스트 설정은 바꾸지 않았다.

T_first와 hazard proxy는 실행 수로 세므로 시계와 무관하다(관찰). oracle과 U_viol은 실행 수가 아니라 파일 시각을 포함한 파일시스템 스냅샷을 보지만, 파일 시각은 실시간 시계로 찍히므로 이 배율의 영향을 받지 않는다고 본다(추론). `TARGET_NEVER_SETTLED`는 타이머가 아니라 event loop 소진 판정이다(`src/inodefence/targets/_node_effect_producer.cjs:516-527`).

| 값 | monotonic 기록값 | 실시간 환산 |
| --- | --- | --- |
| p95 합산 | 1.549 s | 1.419 s (범위 1.413~1.427) |
| p50 합산 | 1.488 s | 1.363 s |
| 스트림당 exec/h, 리포트 내부 시간 합 4448 s 기준, 셀 준비 시간 제외 (생성기 "Summed") | 2428 | 2650 (범위 2636~2662) |
| 스트림당 exec/h, 런처 wall 합 4682 s 기준, 셀 준비 시간 포함 | 2307 | 2518 |
| 집계 exec/h | 해당 없음 | 약 4760 (실경과에서 직접 계산: 셀 구간 4763, 해시 고정 타임스탬프 4758) |

집계값은 스트림당 값의 2배가 아니다. 런처 기준 2518에 평균 동시 실행 1.89 스트림(실시간 환산 셀 시간 합 ÷ 실경과 2267.6 s)을 곱하면 4763이다. 셀이 15개라 마지막 셀은 단독으로 돌았다.

**편차 2. invalid trace와 failed step.** abort 0과 별개로 trace가 invalid인 step이 11개다: D 8 / S-u 3 / R 0. 실패 종류는 `operation_correlation_conflict` 10건과 `malformed_identity` 2건이고(한 step에 여러 건 가능), 전부 `rejected` 종료에 `feedback_eligible=false`다(관찰). 셀 보고서의 `observer_integrity_summary.invalid_steps`는 step `validity`가 invalid인 경우만 세므로 전 셀 0이고, 이 11개는 JSON `item6_dense_signals`의 `observation_failures_total`(8/0/3)에 나타난다. 이와 별도로 `failed` 종료가 10 step(D 4 / S-u 6) 있고 전부 `TARGET_NEVER_SETTLED`다(관찰). oracle은 post-state 기반이고 hit도 0이므로 측정 5·7은 바뀌지 않는다(추론).

**편차 3. 측정 4 미충족.** 등록 실행은 per-case 15셀뿐이라 워커 풀 처리량이 없다. v2.1 주석은 parity가 EXP-0의 전제가 아니라면서도 워커 풀을 나란히 보고한다고 적었다. 레인 4의 비등록 결과 `~/inodefence-evidence/wp-parity-20261104/workerpool/wp-parity-result.json`을 `--parity`로 읽으면 `core_parity_4dim=true`지만, 처리량 줄은 생기지 않고 등록 측정을 대신하지 않는다. 공식 JSON은 premerge와 대조하려고 `--parity` 없이 생성했으며, 줘도 달라지는 곳은 `item4_throughput_parity`뿐이다(관찰). 생성기 원문의 "Parity verdict: None"은 이 때문이다.

**편차 4. boundary 키는 셀 합계다.** 생성기의 `boundary_keys`는 셀별 수의 합이다(D 10 / R 2 / S-u 9). 같은 arm 안에서 중복을 없애면 D 4 / R 1 / S-u 3이다(관찰: steps의 `new_effect_keys` 재집계). 셀 합계를 고유 키 수로 읽으면 안 된다.

**편차 5. 보고서의 타깃 필드.** JSON `targets`는 `["unspecified"]`다. 셀 요약에는 `target`만 있고 생성기가 읽는 `target_id`가 없기 때문이다(관찰). `summaries/index.json`의 15셀은 모두 `target_id=7.5.2`이고 다른 타깃은 없다. `environment`의 `recipe_sha256`도 null이다. JSON은 생성기 출력 그대로 두고 여기에 공개한다.

**편차 6. Python tarfile 미실행, 값 미기재.** 사전등록 대상표(`exp0-pilot-v2.1.md:206,208`)는 Python tarfile 3.12 `fully_trusted`와 인터프리터 버전 문자열, 컨트롤러 image digest를 v2.1에서 채우기로 했다. 실행은 node-tar 1타깃 15셀이고, 기계판독 블록에 Python 타깃이 없으며, 두 값 모두 채우지 않았다(관찰). 컨트롤러 이미지 id는 raw `warmup.log`에 `sha256:d44900e13ed5083db54cefda8833328d4da61148f62213d86f07afa78191d7a4`로 남아 있다(관찰).

**편차 7. 엔진과 등록 커밋 사이의 커밋.** `exp0-pilot-v2.1.md:148`은 `engine_sha`가 머지 완료 main HEAD이고 등록 커밋이 그 위에 온다고 적었다. 실제로는 `b609981`과 등록 커밋 `23e5c66` 사이에 #218 `d7ab2a6`이 있다. #218은 `Makefile`, `docs/LOG.md`, `scripts/regression_check.py`, `tests/test_regression_check.py`만 바꿨다(관찰). 캠페인 경로 밖이고 실행은 정확히 `b609981`에서 했다(추론, 등록 기록의 `engine_sha`와 일치).

**편차 8. 대상표의 image prefix.** 대상표(`exp0-pilot-v2.1.md:205`)의 prefix `21d8a0e3a5c5`는 실행 이미지 `22c8734f`와 다르다. 실행은 기계판독 블록의 동결 값과 일치한다(관찰). 차이는 [노출 원장](../preregistration/exposure-ledger.md) L15-16이 구분한다(맥 빌드, 이 호스트 빌드).
